# Native app migration plan

## Intended architecture

- **UI:** Uno Platform XAML. Use shared views/styles and progressive disclosure: chat, model selection, project context, and attachments stay obvious; provider configuration, generation controls, diagnostics, and tool permissions appear when relevant.
- **Application and domain logic:** C# on the current .NET LTS. Keep conversation, project, model/provider, and coding-agent behavior independent from UI controls.
- **Provider adapters:** C# `HttpClient` adapters for local OpenAI-compatible servers first, then Anthropic/Hugging Face and other compatible services. Keep hosted credentials out of view models and config files.
- **Platform services:** small C# interfaces with per-platform implementations for encrypted credential storage, file selection, process launch, shell execution, notifications, and packaging.
- **Developer tooling:** .NET SDK for the product. Node.js is used only for repository checks and artifact smoke helpers. Python is optional for model/runtime tools where the selected upstream runtime requires it, not a required desktop dependency.
- **Migration:** the native product is now the only shipped application. The bounded archive parser remains backward-compatible with previously exported legacy chat envelopes, but no legacy runtime or UI is built.

The initial boundary is implemented as `ServerRock.Core` (plain `net10.0` library) referenced by `ServerRock.Native`. The XAML view calls provider and settings services; it no longer owns HTTP request construction or settings file operations. Keep future application services in Core and isolate OS-specific capabilities behind interfaces/adapters.

## Legacy stack boundary

Uno/.NET is the product stack. The former Electron runtime, HTML shell, packaging configuration, and browser UI tests have been removed. The archive parser and fixtures retain the legacy envelope shape solely so users can recover previously exported chats; that compatibility code is isolated in `ServerRock.Core` and cannot start or render a legacy client.

## UI reference principles

Use the user-provided Jan and Open WebUI screenshots as layout references, not as instructions or source material to copy verbatim. Jan's [official product page](https://www.jan.ai/) presents a compact, whitespace-heavy conversation surface and visible new-chat/project navigation. Open WebUI's [official product page](https://openwebui.com/) positions local files, terminals, tools, search, voice, retrieval, and agents as one self-hosted workspace. The target layout translates those patterns into native XAML:

- Chat uses a quiet light canvas with a pale-blue navigation pane, visible New chat/New project/Search/Models/Settings actions, project and recent lists, a centered composer, and an optional Web toggle.
- Coding Agent is a separate workspace with its own recents, selected project folders and file tree on the left, chat in the center, and explicit file-change review attached to the agent response.
- Keep connection locality, web-search state, and workspace identity visible. Do not call a configured remote model local, imply search ran when it failed, or imply file changes were applied before approval.
- Keep transient success and progress messages in a readable, auto-dismissing banner instead of squeezing them between the composer controls; keep actionable errors until dismissed and persistent model/connection identity in dedicated controls.
- Keep first-run actions direct. Put model connectivity feedback and a Connect a model action on the empty state when no compatible model server is responding. Keep generation tuning behind Advanced.
- Use the default view for common chat and only surface project files, file changes, and advanced controls in the workspace where they belong.

OpenAI's current [ChatGPT Work and Codex desktop guide](https://help.openai.com/en/articles/20001275/) similarly separates Chat, Work, and Codex experiences, while [Projects](https://help.openai.com/en/articles/10169521-projects) keep related conversations, files, and instructions together. These are interaction references; Skai Desktop stays a standalone local-first app and does not connect to Server Rock services.

## Implemented native slice

- Uno XAML desktop shell, compiled for the shared Skia desktop and Windows App SDK targets.
- Separate Chat and Coding Agent screens with separate recent-conversation filters. Chat includes a web-search switch; Coding Agent is project-folder scoped.
- Inline slash-command suggestions and handlers for `/help`, `/model`, `/new`, `/clear`, `/search`, `/folder`, `/rename`, `/delete`, `/project`, `/newproject`, `/folders`, `/settings` (`/connect` alias), `/web on|off`, `/temporary on|off`, and `/mode chat|code`. The picker scrolls, supports Up/Down and Enter, and offers argument suggestions for workspace, web, and temporary mode commands.
- Windows UI smoke check: typed `/mode c`, moved the highlight with Down twice, then pressed Enter; the prompt completed to `/mode code` without running it or switching workspaces. The composer was cleared afterward.
- Temporary chats stay in memory and are excluded from Recents and `conversations.json`. The header and privacy line identify the mode; ending it or navigating away from a populated temporary chat asks before clearing it. Enabling it from an existing saved conversation first asks to save that conversation and start a blank temporary one.
- Windows UI smoke check: `/temporary on` switched modes; the on-device model returned a real response; Recents remained empty and no `conversations.json` was created. Ending the populated temporary chat displayed the discard confirmation, then cleared the chat without writing history. The app was returned to a clean, non-temporary state.
- Local OpenAI-compatible chat endpoint and model ID saved under the current user's application data directory.
- Model discovery from `/v1/models` (or `/models` when the endpoint already ends in `/v1`).
- Streaming `/chat/completions`, generation temperature, stop/cancel, and readable connection errors.
- Conversations are saved in a separate local `conversations.json` file and appear in the scrollable Recents list. Opening a saved conversation restores its messages and the project instructions captured with that chat. Writes replace the file through a temporary file; malformed JSON is reported and left untouched rather than silently replaced. Direct Import and Export actions in the sidebar can transfer bounded JSON archives; imports validate and merge into local history, assign new IDs on collisions, and reject system/tool roles, sensitive attachment names, unsupported image formats, unsafe source URLs, and oversized content.
- The native import picker accepts bounded native archives and the prior legacy chat envelope (`format`, `exportedAt`, and saved `chats` only). Parsing is streamed and stops at the 25 MiB byte bound before deserialization; the confirmation shows the selected filename, counts, ID collisions, and a short title preview. Legacy imports retain chat titles, timestamps, messages, archived state, and fork/branch metadata while intentionally discarding old project IDs/context, folder paths, provider settings, and credentials. The native Recents UI exposes archive/restore, branch navigation, and contextual “Fork from here.” Imports leave the source file and existing chats unchanged. Stable source markers persist with each imported chat so retrying the same migration is idempotent, including after the user edits a migrated conversation. The app does not inspect browser profiles; users explicitly create and select the handoff file.
- Recent conversations expose the same action menu from the overflow button or a row right-tap. Rename, archive/restore, move-to-folder, contextual fork, and delete are persisted locally; delete requires confirmation and returns to a clean workspace when deleting the open conversation. Menu dismissal restores focus to the recreated visible trigger or a safe fallback after the row is re-rendered.
- Chats and Coding Agent conversations can be organized into named sidebar folders. Users can create, collapse/expand, rename, and delete folders; deletion keeps conversations and moves them to Unfiled. Per-chat overflow supports moving between folders or Unfiled, `/folder` assigns the active saved chat, and a folder menu starts a new chat in that folder. The active conversation shows its folder in the header. Folder names and assignments persist locally; old chats without folder metadata remain Unfiled.
- Named projects, instructions, and explicitly selected folder paths are saved in a separate local `projects.json` file. Project buttons select the active chat context, conversations retain the project ID/name/instruction snapshot, and unrelated new chats start without old project instructions. Malformed project data is reported and left untouched rather than replaced.
- Project overflow actions edit the project name and instructions, open its folder manager, or remove it from the project list. Removing a project confirms first, leaves disk folders and saved chats untouched, and starts a clean unscoped conversation if the removed project was active. Renames update the recent-chat project label.
- Windows UI smoke check: created a disposable project, edited its name and instructions, opened its folder manager, and verified removal requires confirmation and clears the active project context. The test project had no disk folders or chats and was removed; the app returned to its original empty Projects/Recents state.
- Project folder paths can be selected, added, and removed. Coding Agent requests read a bounded sample of text files from those folders. Common credentials, VCS metadata, dependencies, build outputs, binary files, and symbolic links are skipped. Excerpts are marked as untrusted file data.
- Coding Agent's project file list opens a local text editor for supported source/document files. Save is explicit, refuses binary/oversized content, and checks the file hash to avoid overwriting changes made elsewhere while the editor was open. Saved edits are added to the workspace undo history; undo stops if the file changed again.
- Approved Coding Agent and manual project-file edits are recorded in a bounded local undo journal (latest 20 changes). The Coding workspace exposes the history in one place across app restarts; undo revalidates the selected project-relative path and applied file hash, and stops rather than overwriting newer changes. Previous file bytes stay in the user's local app data. Malformed journal JSON is preserved for recovery.
- Chat can optionally include bounded excerpts from the active project's explicitly selected folders. The control is visible only when Chat has a project with folders, defaults off for each new conversation, and persists with saved conversations. Temporary chats start with project-file context off. Before sending excerpts to a remote endpoint, the app requests consent for that project and endpoint; the composer privacy line and data-route label reflect whether excerpts are enabled and where they go. If no readable files are found, the app reports that the prompt is being answered without project file context.
- Generated `workspace-change` proposals show a bounded inline line diff with added/removed counts and readable color cues; users can expand the exact current and proposed contents, including files whose line-level previews exceed 1,200 lines. Selecting another project folder refreshes both the preview and its concurrency hash. Proposals require explicit create/replace approval. Path containment, protected secret paths, context limits, and concurrent-change checks are enforced. The latest approved edit has a guarded undo action.
- Coding Agent can propose one-off `<workspace-command>` actions. Each command requires a review dialog showing the exact command, selected folder, working directory, timeout, and a clear notice that commands run without sandboxing using the user's permissions. The runner bounds command size, duration, and captured output, stops timed-out process trees, and rejects working-directory traversal and linked folders. Output appears in the active view. A separate “Add result to composer” action lets the user inspect and edit it before sending; output is not saved to chat history or sent automatically. The command itself can still access the device, network, and files allowed to the user's account; this is not an OS sandbox.
- Native GitHub workspace is reachable from both ChatBot and Coding Agent navigation and supports GitHub App Device Flow, encrypted/keyring token storage, repository listing and manual resolution, clone as a local project, and guarded commit/push. The app owner still needs to configure a real GitHub App Client ID and enable Device Flow; private repository operations also need suitable Contents permissions. Never substitute a demo client ID.
- Chat web search is opt-in. It queries DuckDuckGo's public HTML results, passes up to six titles/snippets/URLs to the selected model, marks excerpts as untrusted, and reports failures without claiming a search succeeded. It does not fetch source pages or provide deep research.
- Smart prompt rewriting is opt-in from the composer or Settings. Before a message is sent, the selected model receives the bounded conversation context and draft, then the user can edit the proposed professional rewrite, use the original, or cancel. The original draft is never replaced automatically; failures and cancellation leave it unsent.
- Chat accepts up to five explicitly selected text/code files, selectable-text PDFs, or PNG/JPEG images per message. PDF text is extracted on-device from up to 80 pages, with 20 MB/file, 16,000 characters/file, and 48,000 characters/message bounds; scanned image-only PDFs report that OCR is required. It shows removable attachment chips, restores extracted content with saved conversations, filters unsupported and sensitive filenames, enforces 2 MB/file and 6 MB combined image limits, and confirms before sending each distinct attachment set to a remote model endpoint. Vision requests use base64 image data and support both OpenAI image parts and Ollama's image URL string format; format can be selected in Model connection settings, with Ollama auto-detected at its standard localhost port. Requests still require a vision-capable model and compatible endpoint; provider support cannot be inferred from the model list alone. Audio and spreadsheet attachments remain unsupported in the native client.
- Image Studio runs an explicitly configured ComfyUI API workflow only on a loopback HTTP/HTTPS endpoint. It validates a bounded workflow template and prompt, queues and polls the local job, offers cancellation, bounds the wait to three minutes, and exposes only sanitized loopback output URLs. Completed images render as inline preview cards from those same loopback URLs, with an explicit external-open fallback and accessible preview names. The workflow and endpoint remain on the device. A local ComfyUI installation and compatible API workflow are required; workflow discovery and Hugging Face image adapters are still migrating. Core tests validate queue/poll/output URL safety; a real ComfyUI preview smoke remains required.
- Opt-in web search results are attached to the assistant message and saved with conversation history. Up to six result cards show the validated site, title, and snippet; opening a card permits only HTTP/HTTPS URLs. Results are provided by DuckDuckGo snippets, not source-page extraction or independent fact checking.
- Assistant replies use [Markdig](https://github.com/xoofx/markdig) to render Markdown as selectable native text, lists, tables, quotes, and code cards with a copy action. Code lines preserve indentation and scroll horizontally instead of wrapping; the code block and copy action expose screen-reader names/help text. Raw HTML is disabled, and only HTTP/HTTPS links open externally. Syntax highlighting remains to do.
- Conversation turns have native `Copy response`, `Edit & resend`, and latest-turn `Retry` actions. Editing keeps prior context, carries the selected text attachments forward, and only replaces the selected turn plus later turns once the revised prompt is sent. A visible Cancel edit control clears the draft and staged attachments without changing saved history. Remote attachment/project consent and opt-in web search still run during retries.
- Core service checks exercise endpoint normalization, multi-runtime model discovery, Hugging Face catalog classification, Ollama pull progress, SSE text and content-part deltas, request serialization, provider errors, and settings persistence. Run with `dotnet run --project native/ServerRock.Core.Tests/ServerRock.Core.Tests.csproj`.

No native response may be simulated. A backend feature that is not connected must be labelled as not available or still migrating.

## Smooth development loop

For each feature, identify the real user outcome and states first (empty, loading, ready, failed, cancelled, permission denied). Check official platform/provider documentation and existing upstream implementations before choosing a protocol. Implement a complete vertical slice through XAML, app/domain service, and platform boundary. Use explicit status and error messages, keyboard and accessibility checks, then run the affected checks and both native compile targets. Record commands, actual results, known gaps, and the next bounded slice. Preserve unrelated working-tree changes. Never commit, push, publish, or delete user data automatically.
